# 檢討紀錄

新的紀錄加在最上面。每筆用這個格式：

```
## YYYY-MM-DD 主題

- 錯在哪裡：
- 怎麼發現的：
- 根本原因：
- 擋法：模板／檢查腳本／ccv／hook／文字規則，擇一
- 改了什麼：檔案與 commit
- 證明：怎麼證明有效；證明不了時寫「未證明」與原因
```

## 2026-11-11 pre-commit 跑測試（接 2026-11-02 測試失敗仍然 commit）

- 錯在哪裡：2026-11-02 那筆用文字規則擋「測試和 commit 串在一起」，沒擋住。session 紀錄中，`node --test … | grep … && git commit` 這種寫法出現 2 次（2026-11-01T13:19Z 與 17:47Z，UTC）。grep 找到 `# fail N` 也回傳成功，`&&` 擋不住。那 2 次測試剛好全過。
- 怎麼發現的：2026-11-11 檢視三個 session 的紀錄時找到。
- 根本原因：當時沒加 pre-commit，理由是「每次 commit 多花約 1 秒」。這個數字在 `3ba9bfe`（2026-11-09 加入 system-stats 測試）之後不成立：2026-11-11 實測全部測試要約 16.8 秒。
- 擋法：git hook。
- 改了什麼：先把測試壓到 2 秒以內（`specs/fast-tests.md`），再讓 `.githooks/pre-commit` 跑 `node --test tests/*.test.mjs`，失敗就擋下 commit。README「維護」表加一列。
- 證明：反向測試。在 `tests/services.test.mjs` 暫時加一個一定失敗的測試，執行 `git commit`：回傳 1，印出 `not ok` 與 `pre-commit：單元測試失敗，已擋下 commit。`，HEAD 不變。還原後全部測試連跑 5 次，都是 `# fail 0`，`# duration_ms` 在 1378～1441。限制：pre-commit 跑的是工作區的檔案，不是 staged 的版本。

## 2026-11-11 用總時間推論測試慢的原因

- 錯在哪裡：`specs/fast-tests.md`（commit `744e9c7`）的 How 只寫了每個測試要幾秒，例如 report-rate-limit「其他測試各約 0.33～0.39 秒」，沒有寫時間花在哪一段。依此決定「同一個檔的測試並行」。實作第 3 輪把 system-stats 的測試改成並行後，11 個測試有 10 個失敗。這一輪沒有 commit。
- 怎麼發現的：第 3 輪實跑單元測試。理想上在規劃寫 How 時，晚了兩步。
- 根本原因：只量了總時間，就把原因推論成「等監控程式」。實際拆開量：`node -e 0` 約 0.01 秒；新建的腳本第一次執行約 0.32 秒，第二次起約 0.00 秒；4 個新腳本同時執行約 0.41 秒。每個測試都新建假的 `cmux` 與 `vm_stat`，並行時第一次執行的等待疊在一起。和 2026-11-09 那筆同樣是「沒有用量測核對就寫數字」，但這次錯的是原因，不是數字本身。
- 擋法：模板。
- 改了什麼：spec 模板的 How 規定：寫到時間、速度的原因時，把一個案例的時間拆成各段，每段附量測的指令與輸出；只量到總時間時，原因寫「未查證」。
- 證明：照新規定重寫 fast-tests 的 How，report-rate-limit 一個測試的 0.33 秒拆成 node 啟動 0.01 秒與假腳本第一次執行 0.32 秒，原因露出來了，決策也跟著改。限制：check-spec 不檢查 How 有沒有拆開，只靠模板文字，下次是否擋得住未證明。

## 2026-11-09 spec 範例數字沒有從資料算

- 錯在哪裡：`specs/system-stats.md`（commit `d8a3c0a`）的資料流範例把已用記憶體寫成 33.69 GiB，正確是 33.64；`progress` 的值寫成 0.7018，cmux 實際存兩位小數 0.70。修正在 commit `3ba9bfe`，沒有 push 過錯的版本。
- 怎麼發現的：33.69 是實作監控程式時第 8 條單元測試失敗；0.70 是實跑 `ccv sys-set` 看到 `sidebar-state`。理想上在規劃寫 spec 時，晚了兩步。
- 根本原因：寫範例值時沒有跑指令，用先前四捨五入的值（24.6 + 3.7 + 5.3）反推。「cmux 存的值」也沒有照模板用 `ccv probe` 讀真實資料，直接沿用 7d spec 的格式。和 2026-11-03 那筆同樣是「沒用真實資料核對」，當時的模板文字規定這次沒擋住。
- 擋法：模板加檢查腳本。
- 改了什麼：spec 模板的資料流範例加「### 數字的來源」，要寫出算出數字的指令與輸出；`scripts/check-spec.mjs` 在資料流範例不是「不適用」時，要求這一小節存在而且有程式碼區塊。
- 證明：反向測試 `checkSpec` 四種輸入：`d8a3c0a` 的 spec（缺小節）與「有小節、沒有程式碼區塊」被擋下；「有程式碼區塊」與「不適用」放行。照新規定在現在的 spec 補上指令並實際執行，算出 33.64、比例 0.7008、85.4%，`sidebar-state` 是 0.70，和範例一致。限制：腳本只確認有附指令，不確認算得對。

- 根本原因：照 cmux 文件寫程式與 spec，沒有用真實資料核對。單元測試的假資料也照文件寫，所以測不出來。

- 證明：修正後實跑 agent-dot、agent-lock PASS（run `20261103T153303-1ffx`）。模板規定本身是否擋得住下一次，未證明：要等下一個用到 cmux 欄位的功能。

## 2026-11-02 測試失敗仍然 commit

- 錯在哪裡：一輪實作把跑測試和 commit 串在同一個指令，測試失敗時仍然 commit 了。
- 怎麼發現的：看指令輸出才發現，事後用 amend 修正（commit `8644b9f`）。
- 根本原因：指令用 `;` 和 `&&` 混著串，測試失敗沒有中斷後面的 commit。
- 擋法：文字規則。git hook 可以在 pre-commit 跑全部測試，但每次 commit 都會多花約 1 秒，還沒決定。
- 改了什麼：ship-cc-cmux 的「注意」寫明跑測試和 commit 分開下指令。
- 證明：未證明。之後同一個 session 又串在一起一次，那次測試剛好全過。文字規則擋不住，下次再發生時，改成 pre-commit 跑測試。
