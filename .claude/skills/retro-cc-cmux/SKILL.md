# 檢討 cc-cmux 的錯誤

這個 skill 的方式和 plan-cc-cmux 一樣，參考 grill-me：一次一題，每一題都寫出 How、Why 與建議。事實自己查，附上出處。

- **How（現在怎麼做）**：錯誤發生時，程式、skill 或流程實際怎麼運作。這是事實，附出處，例如 commit hash、run id、檔案行號。
- **Why（為什麼要這麼做）**：這一題的答案會影響什麼。

這個 skill 只改流程，不改功能：可以改 `.claude/skills/`、`scripts/`、`.githooks/`、spec 模板。不改 `sidebars/`、`tests/`；功能的修正交給 plan-cc-cmux 與 implement-cc-cmux。

## 兩種模式

- **手動模式**：使用者直接啟動時。一次問一題，等使用者回答再問下一題。
- **自動模式**：ship-cc-cmux 呼叫時。每一題照樣寫出 How、Why、建議，直接採用建議，不等回答。採用的建議寫進 `log.md`，最後由 ship-cc-cmux 回報給使用者。

自動模式中，某一題沒有明確的建議可選時，停下來問使用者。

## 1. 先查事實

- 錯誤的產出：哪個檔案、哪個 commit、哪個 run。
- 錯誤發生前後的紀錄：`git log`、`~/.cache/cc-cmux-verify/<run>/actions.log`、spec 的決策表。
- `log.md` 的舊檢討：同樣的原因以前有沒有出現過。

## 2. 要問的題目

照順序問。

1. **錯在哪裡**：哪個產出錯了？影響到哪些已經 commit 或 push 的東西？
2. **怎麼發現的**：哪一步抓到的？理想上應該在哪一步就抓到？差了幾步？
3. **根本原因**：哪個假設錯了、哪個來源不可靠、哪個步驟被跳過？不接受「我錯了」「沒注意到」這種答案。
4. **能不能用系統擋**：照這個順序考慮，選第一個擋得住的：
   1. 模板（例如 `spec-template.md` 加一節或一條填寫規定）
   2. 檢查腳本（例如 `scripts/check-spec.mjs`），由 pre-commit 執行
   3. ccv 指令（例如 `ccv probe` 讀真實資料）
   4. git hook 或 Claude Code hook
   5. 文字規則（skill 或 CLAUDE.md），只有前面都擋不住時才用
5. **改哪裡**：改哪個檔案、改成什麼。改動要小，一個原因一項改動。
6. **怎麼證明改進有效**：用這次的錯誤重新跑一次，看改進後會不會被擋下或露出來。例如：
   - 拿出錯前的資料，照新模板重填，錯誤會不會在表上露出來。
   - 對檢查腳本做反向測試：故意放一份有錯的檔案，確認被擋下。

## 3. 改進

1. 照第 5 題改檔案。
2. 照第 6 題證明有效。證明不了時，寫「未證明」與原因，不要寫成有效。
3. 每項改動各一個 commit。commit message 寫出：錯誤、原因、改了什麼、怎麼證明。
4. 在 `log.md` 最上面加一筆紀錄，格式見該檔。和改動一起 commit。

## 4. 回報

列出每一題的答案、改了哪些檔案、各自的 commit，以及證明的結果。

手動模式下，回報後問使用者：「這次的改進確認無誤嗎？」

## 注意

- repo 是 public。不要寫本機絕對路徑、帳號名稱、公司名稱或終端機內容。
- 同樣的原因在 `log.md` 已經出現過，代表上次的改進沒有擋住。這次要選更前面的擋法，例如上次是文字規則，這次改成模板或檢查腳本。
- 數字從資料計算，不憑印象寫。
